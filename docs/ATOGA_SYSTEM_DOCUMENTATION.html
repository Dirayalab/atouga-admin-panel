فهرس المحتويات

    الجزء 0 — الملخص التنفيذي والنطاق

    هذه الوثيقة مرجعٌ معماريٌّ متكامل لمنظومة «ATOGA MARKET» المكوّنة من أربع واجهات تعمل فوق خلفية واحدة: تطبيق الزبون، تطبيق المدير، تطبيق السائق-المجهّز، ولوحة الإدارة المستضافة على GitHub Pages. الغرض من الوثيقة: تمكين أي مهندس من إعادة بناء المنظومة كاملة بضغطة واحدة بالاعتماد على هذا الملف فقط، عبر سلسلة أوامر جاهزة، ومخطط قاعدة بيانات كامل، وكل الإعدادات، وقائمة مفاتيح مطلوبة في بداية المشروع، وقائمة أسئلة استيضاحية على من يطلب البناء.

    أهداف النظام

    • متجر إلكتروني للمواد الغذائية (جرد، تصنيفات، بنرات، كوبونات) بتجربة عربية/فرنسية (RTL).
    • محفظة إلكترونية يدفع بها الزبون وتشحنها الإدارة (لا يُعدّل رصيدها من العميل).
    • إدارة كاملة: منتجات، تصنيفات بأيقونات، تسويق (بنرات/كوبونات/إشعارات)، زبائن، أوقات عمل، موظفون.
    • واجهة سائق/مجهّز: استقبال الطلبات لحظياً (Realtime) بنظام «أول من يضغط يستلم» (Atomic Claim)، قائمة تجهيز تعيد حساب الإجمالي عند نفاد صنف، طباعة فاتورة حرارية Bluetooth، وإشعارات تعمل حتى عند إغلاق التطبيق.
    • لوحة إدارة (Super Admin) لاعتماد الطلبات وإنشاء الحسابات، وقسم «إخراج التطبيق من التجربة» لتنظيف البيانات التجريبية بتحكّم دقيق.

    الجزء 1 — المنهجية وتاريخ المشروع

    المبادئ المعتمدة

    • RLS أولاً: كل جدول يملك سياسات صفوف؛ أية كتابة من العميل تخضع لسياسة `with check`، والحسابات المتميّزة تُدار بدوال SECURITY DEFINER.
    • مفتاح publishable فقط في الكلائنات: لا يُنشر service_role إطلاقاً في أي واجهة عميل.
    • ترقيات قابلة لإعادة التنفيذ: `create or replace`، `add column if not exists`، `on conflict do nothing`.
    • التجربة تُبنى وتُختبر مباشرة: بنية تدريجية، وكل مرحلة مكتفية وظيفياً.
    • الهاتف = اسم مستخدم: مدخل الزبون رقم هاتف يتحول داخلياً إلى بريد وهمي `@atoga.com` عبر GoTrue (لا OTP).

    الجزء 2 — الهندسة المعمارية والطبقات

    منظومة سحابية: أربع واجهات عميل لا تحفظ حالةً في الخادم إلا عبر Supabase؛ وكل عملية متميّزة تُنفَّذ من خلال Roles/RLS أو دوال SECURITY DEFINER أو Edge Functions. الصور تُرفع مباشرة إلى ImageKit (وليس storage Supabase).

    اتجاه البيانات

    • الواجهات الأربع → Supabase REST/RPC/Realtime بمفتاح publishable فقط (RLS تحكم الوصول).
    • الزبون والسائق → FCM عبر `send-push` (من triggers في القاعدة عبر pg_net).
    • المدير → ImageKit لرفع صور المنتجات/البنرات (لا تُحفظ في Supabase Storage).
    • اللوحة ← نفس الخلفية بجلسة Super Admin ودوال محمية.

create policy "Read active categories" on categories for select using (is_active = true);

create policy "Users own cart_items/favorites/addresses" ... using (auth.uid() = user_id);

create policy "Users cancel own pending order" on orders for update
  using (auth.uid() = user_id and status = 'received')
  with check (auth.uid() = user_id and status = 'cancelled');

    4.4 أهم دوال RPC (عرض، إدارة، توصيل، تنظيف)

    قائمة عامة + نموذجا RPC للاستلام الذرّي وتعديل التوفر 
    -- الاستلام الذرّي: أول من يضغط يملك الطلب (قفل صف + حالة)
create or replace function public.claim_order(p_order_id uuid)
returns public.orders
language plpgsql security definer set search_path = public
as $$
declare v_order public.orders;
begin
  if not public.is_fulfillment_staff() then raise exception 'forbidden'; end if;
  select * into v_order from public.orders where id = p_order_id for update;
  if not found then raise exception 'order_not_found'; end if;
  if v_order.status <> 'received' then raise exception 'order_already_claimed'; end if;
  -- محفظة: الخصم النهائي عند التجهيز
  if v_order.payment_method = 'wallet' then
    -- (يخصم المحفظة ويحسب الإجمالي من أصناف الطلب)
    perform public.prepare_order_wallet_payment(p_order_id);
  end if;
  update public.orders
     set status='preparing', packager_id=auth.uid(), claimed_by=auth.uid(),
         claimed_at=now(), preparing_at=coalesce(preparing_at, now())
   where id = p_order_id returning * into v_order;
  return v_order;
end $$;

    الجزء 5 — تطبيق الزبون (Customer)

    الموضوع: أحمر #E53935 ثيم فاتح عربي/فرنسي RTL 6 تبويبات: الرئيسية، السلة، المحفظة، طلباتي، الكوبونات، حسابي.

    تدفقات أساسية

    • المصادقة: الهاتف → بريد وهمي 0555…@atoga.com → GoTrue password؛ أو Google OAuth بمخطط atogamarket://login-callback.
    • الطلب: سلة ← عنوان (منطقة/خريطة/دبوس/عكس إحداثيات عبر Nominatim) ← كوبون ← COD أو محفظة ← إنشاء طلب (wallet عبر RPC) ← شاشة النجاح.
    • التتبّع الحي: شاشة الطلب تستمع بثّ orders + order_items؛ يظهر «نفد المخزون» ويُحدَّث الإجمالي فوراً.
    • التجميد: banner + تعطيل الشراء + منع خادمي عبر trigger.
    • الإشعارات: FCM بأسلوب Big Picture + فتح التتبّع من النقر.

    أبرز التفاصيل التقنية

    • الدخول باليوزر نيم عبر resolve_username؛ الحسابات الرئيسية محمية؛ أدوار التوصيل محجوبة من تطبيق الإدارة.
    • الكتالوج: منتجات (رفع صورة ImageKit، سعر/سعر عرض، وحدة، إظهار/إخفاء، حذف) وتصنيفات (أيقونة + بحث عربي/فرنسي/إنجليزي، ترجمة تلقائية، حذف يبقي المنتجات بلا تصنيف).
    • التسويق: بنرات (صورة/لون، محاذاة/تكبير)، كوبونات (نوع/حدود/ترحيبي)، إشعارات فورية ومجدولة (send-push).
    • المحفظة: شحن/خصم (credit/debit RPC) وسجل الحركات.
    • الزبائن: بحث وإحصاءات وتجميد بسبب (يعرضه الزبون فوراً عبر Realtime على profiles).
    • الموظفون: إنشاء عبر admin-create-staff (يُحوّل اليوزر إلى بوتبرّيد username@atoga.com)، تعديل، كلمة مرور، تجميد، حذف، إحصاءات.

    الجزء 7 — تطبيق السائق-المجهّز (Driver)

    الموضوع: أخضر #1CB01C ثيم فاتح أقسام: الطلبات، الإحصاءات، الحساب. يعتمد على Supabase Realtime في الاستقبال، وعلى FCM عند إغلاق التطبيق، وعلى طابعة حرارية Bluetooth للفاتورة.

    آلية الاستلام الذرّي (أهم نقطة)

    1. الزبون يُنشئ طلباً → trigger orders_new_order_push يبثّ إشعار FCM + القائمة Realtime تتحدث عند الجميع.
    2. أول سائق يضغط «تجهيز الطلبية» يستدعي claim_order الذي يقفل صف الطلب (FOR UPDATE) ويحول الحالة إلى preparing.
    3. الطلبات الأخرى ترد بـ order_already_claimed ويختفي الطلب من طوابيرهم فوراً (Realtime).
    4. الدفع من المحفظة يُخصم عند التجهيز في نفس المعاملة.

    التنبيه الشامل (حالات الجهاز)

    الحالةالآليةالنتيجة
    مفتوح (Foreground)Realtime → NewOrderPopuppopup + نغمة (مسار ALARM) + اهتزاز
    خلفية (عملية حيّة)خدمة أمامية flutter_background_service + FCMإشعار نظام heads-up بصوت/اهتزاز
    مغلق/مقتولFCM notification + channel driver_ordersإشعار نظام heads-up (يُفتح عند النقر)

    الطباعة الحرارية Bluetooth

    عبر unified_esc_pos_printer (Bluetooth Classic SPP): فحص مقترنات، حفظ الطابعة المفضّلة، اتصال ثم طباعة فاتورة ESC/POS. العربية تُرسل كصورة (raster عبر Flutter Text engine) لأن الطابعات لا تدعم النص العربي. المحتوى: رقم الطلب/التاريخ/العميل/الهاتف/المنطقة/العنوان/الأصناف/المجاميع/الدفع + قصّ الورق.

    1,160 دج تجهيز الطلبية طلباتي النشطة (1) #6027EA8قيد التجهيز حي الزهور COD · 850 دج الطلباتالإحصاءاتالحساب
    طابور السائق: طلبات جديدة (الكّل) + نشطة (لي).
    كيف تلتقطها: أنشئ طلباً من الزبون وأنت داخل تطبيق السائق.
    تفاصيل الطلب: قائمة التجهيز (إزالة صنف تعيد الحساب) + الانتقالات.
    كيف تلتقطها: استلم طلباً واضغط عليه.

    الجزء 8 — لوحة الإدارة (Admin Panel)

    صفحة ثابتة على GitHub Pages (teomar007.github.io/atouga-admin-panel) مكتوبة بـ HTML/JS خام + Tailwind CDN، تتصل بنفس Supabase بمفتاح publishable، ولا تعرض أي شيء إلا لمستخدم super_admin: الدخول بالبريد/كلمة المرور ثم تحقق get_my_staff_role.

    الأقسام

    • طلبات الوصول: اعتماد كمدير/مسوّق أو رفض طلب (admin_approve/reject_access_request).
    • إنشاء حساب: يوزر نيم + باسورد + دور (سائق/معبئ/إداري) عبر admin-create-user (أو staff)، فوراً بلا انتظار.
    • الحسابات: تعديل، تغيير كلمة مرور، تجميد/تفعيل، حذف (الرئيسي محمي).
    • إخراج التطبيق من التجربة (Go Live): ملخّص أعداد كل الجداول + تحميل نسخة احتياطية + حذف انتقائي عبر admin_golive_summary/admin_golive_delete/admin_backup_snapshot — يفصل كل مكوّن (حسابات، كوبونات واستهلاكها، طلبات وعناصرها + حركات المحفظة + تصفير الأرصدة تلقائياً، سلات، مفضلة، عناوين، منتجات، تصنيفات، بنرات، حملات، مجدولة، طلبات وصول) بتأكيد كتابة «حذف»، وبدون زر «حذف الكل».
    لا تُحذف من اللوحة: روابط الدعم، أوقات العمل/الورديات، مناطق التوصيل — إدارة المسيّر النهائي فقط.
    لوحة الإدارة — تبويب «إخراج التطبيق من التجربة» (لقطة حقيقية متاحة على Pages).
    كيف تلتقطها: افتح teomar007.github.io/atouga-admin-panel/dashboard.html وسجّل دخول super_admin.

    الجزء 9 — الأمان والامتثال

    • RLS على كل جدول؛ أي وصول كتابة عميل مقيد بـ with check (صاحب الصف/الدور فقط).
    • دوال SECURITY DEFINER للعمليات المتميّزة (استلام ذرّي، محفظة، إدارة، تنظيف) مع فحص الدور داخلها (is_fulfillment_staff/is_super_admin/…).
    • مفتاح publishable فقط في الكلائنات؛ service_role في Edge Functions/ترقيات فقط.
    • حماية الحساب الرئيسي: guard_primary_admin يمنع حذف/تعديل dirayalab@gmail.com، واللوحة تستثنيه وتحسينك أيضاً في admin_golive_delete.
    • المحفظة محمية: revoke UPDATE على العمود wallet_balance؛ الدفعات عبر RPC فقط.
    • التجميد: trigger يمنع الطلب، والواجهة تعرض البانر.
    • الإشعارات: القناة بصوت alarm (تُسمع بالصامت)؛ أذونات POST_NOTIFICATIONS/BLUETOOTH/FOREGROUND_SERVICE في المانيفست.
    • أسرار: Vault للمفاتيح الداخلية (push_*)، Secrets للـ FIREBASE_SERVICE_ACCOUNT؛ لا تُطبع.
    • الطباعة/البلوتوث: BLUETOOTH_CONNECT/SCAN + legacy، وطلب إذن وقت التشغيل.
    • الحذف النهائي: DML فقط (DELETE صفوف) — لا DDL في clean-up؛ نسخة احتياطية قبل الاستخدام.

    الجزء 13 — أسئلة المقابلة مع طالب البناء

    1. هل تملك Firebase من قبل أم يجب إنشاء مشروع جديد ضمن حسابك؟
    2. ما عملة المتجر وتنسيقها (دج/دينار/…)، وعدد اللغات المطلوبة؟
    3. هل ستستخدم Google Maps لدبوس العنوان أم OSM/خريطة محلية؟ (المنظومة لم تستخدم API Key للخرائط.)
    4. ما سياسة المحفظة: شحن نقدي فقط؟ هل نُبقي المحفظة أم نلغيها؟
    5. مناطق التوصيل وأسعارها وحدّ «التوصيل المجاني»؟
    6. أوقات العمل: فترتان/الجمل؟ هل تُدار من المدير فقط؟
    7. المنتجات: صور من ImageKit أم من وسيط آخر؟ وهل نحتاج مخزوناً فعلياً؟
    8. الطابعة الحرارية: طراز (Bluetooth Classic أم BLE)؟ هل نضيف النسخ الاحتياطي للطباعة؟
    9. سلوك الإشعارات: تنبيه صوتي في الوضع الصامت؟ خدمة أمامية؟
    10. من هم «المدير العام» وحدود الأدوار (driver/packager/dual)؟
    11. هل يتطلب Google Sign-In إضافة SHA-1 لديك؟
    12. هل ننشر على Google Play (AAB) أم تثبيت مباشر APK؟
